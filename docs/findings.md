# Findings so far

From one developer's Claude Code logs, Aug 6 - Sep 16, 2026. Aggregate numbers only.

Each number here is as of the entry that records it, not as of today. The entries reach to Sep 16 or Sep 17 depending on when they were measured, so an entry's own dates govern where a figure disagrees with this line. Entries are not rewritten when the logs grow; a re-run is recorded on its own instead, and the one below at the end covers every numbered gate as of 2026-09-21. [what-ccdrift-caught.html](what-ccdrift-caught.html) was recomputed through 2026-09-19 on 2026-09-21, and its day-by-day figures are the later ones: it now shows Sep 17 scoring z = -4.57 on its own without flagging, and puts the turn-by-turn CUSUM's first false-alarm-free threshold at h = 20 rather than the h = 8 that 12 clean days gave.

- **Cache: a real signal.** A Claude Code caching regression (versions 2.1.233-2.1.258, in use Aug 16 - Sep 4) is flagged from Aug 18. Its first days score z = -3.8, -5.4, -2.8, -3.2 against a cutoff of 3.0, so a flag takes 3 deviant days among any 4: once Claude Code's 30-day transcript cleanup deleted part of Aug 15-16, requiring 3 in a row missed it. With the incident left out, a 5% drop is caught from all 3 starting days in the 12 clean days that remain.
- **Following an incident.** Replaying the daily check once for each day from Aug 17 to Sep 16, the run on Aug 22 flags the caching regression from Aug 18, on 2.1.235 and 2.1.233, with ~5.6M tokens re-cached so far. Judged against the 14 days before its first flagged day (Aug 6, 7, 15, 16, 17), every day of the regression from Aug 18 to Sep 1 scores z ≤ −3.1. Against a rolling baseline z was back to about 0 by Aug 26, while 5–10% of prompt turns still missed. Pooling 3 days, the run on Sep 7 finds it back to normal from Sep 4 and closes it with Sep 3 as its last day. That alert names 2.1.247 and 2.1.261: on the CLI main thread Sep 4 still ran 2.1.247, with no misses in 38 prompt turns, and Sep 5–6 ran 2.1.261 (2.1.259 appeared only in SDK sessions, 2.1.260 in 12 responses on Sep 4). Judging single days instead closed it on Sep 4 "from Sep 2", though Sep 3 still had a miss. From Aug 18 to Sep 3 missed prompt turns re-cached ~16M tokens beyond the usual miss rate; all misses from Aug 16 to Sep 4 wrote 17.6M. The replay sent no other alert: no Haiku flag, setting change or blank cache metric. As 0.4.0 shipped, a first check on Sep 16 with no state sent no alert, since the regression began more than 14 days earlier, and built an 8.8 MB history.
- **Haiku: a real signal on the main thread**, which never uses Haiku, so a 5% shift is caught from every starting day. Subagent Haiku bursts make the all-turn share noisy: on 5 synthetic logs it was falsely flagged on 3 (on 1 when the deviant days had to be in a row), the main thread on none.
- **Effort: not detectable from one user's logs.** Over the 12 clean days its daily level swung between 0.33 and 0.67, more than a 70% cut in thinking tokens moves it, so no size of drop was caught, on all turns or the main thread. Detecting it points to pooled data from many users.
- **Effort with logged thinking tokens.** Claude Code logs a thinking token count on 52% of responses (11466 of 22181, leaving out Aug 16 – Sep 4); it tracks the signature estimate at r = 1.00. Over the clean days the daily effort level ranges 0.33–0.59 with logged counts against 0.33–0.67 with the estimate on all turns, and 0.24–0.64 against 0.27–0.74 on the main thread. With logged counts the effort sweep catches no drop from every start on all turns or the main thread, the same as with the estimate.
- **Turn latency: too noisy to watch.** 658 main-thread turn durations over 13 clean days, the last of them Sep 16 up to the run. The daily median turn takes 104.5 s (range 30.4–204.7, spread 0.48), and the daily flag rule catches no slowdown up to ×2 from every start (×2 from 2 of 4), with no clean days flagged without a planted slowdown. The logged `messageCount` can't normalise this: it counts the whole session so far, not the turn. On 1,685 main-thread turns it equals the user, assistant, attachment and system records logged before it in the session on 83%, and on 97% of 1,654 consecutive turns it grows by exactly the records added in between; its median is 2,473, while a turn holds a median of 12 user and assistant records. Duration per message (daily median 51 ms, range 14–94, spread 0.84) therefore falls as a session grows, whatever the speed, so it isn't a latency measure; it also catches no slowdown up to ×2.
- **Session-start context: steady enough to alert on.** 34 sessions; per version the median ranged from 46.3k to 132.0k, and every version with 3 or more sessions stayed within a spread of 0.057 (MAD over median). Asked what the rule ccdrift ships finds (every session measured against its own project's recent level, over all projects together and over each project on its own), it reports one step: 104k -> 128k from 2026-08-27 to 09-05, its sessions on 2.1.240, 2.1.260 and 2.1.261, a version none of its baseline sessions ran. The second step this entry used to record, 128k -> 54k from 2026-09-10, was the project switch G12 describes: the pooled rule that found it was reading work moving to two smaller projects created that week. The gate no longer asks that every step come with a new Claude Code version (a project's own CLAUDE.md, skills or MCP servers step its sessions with no update at all, which is the change G12 measures) and reports the versions beside each step instead; the spread condition stands. G2 passes, so ccdrift alerts on session-start changes.

- **Early warning on cache misses: passes, on thin evidence.** A Bernoulli likelihood-ratio CUSUM on new-prompt misses (usual rate against 5%) with h = 4 caught a planted 5% miss rate in a median of 26 new-prompt turns (38 of 40 runs). Its 0 false alarms cover only 2 complete clean days, Sep 14 and 15 (and Sep 16 up to the run), the only ones whose 14 days before their week held the harness's 100 new-prompt turns; with the check's 200, no complete clean day qualifies. It alarmed on the real regression at 2026-08-18 21:55 UTC, 4 days before the daily check's alert, only because the harness then falls back to the 59 new-prompt turns before Aug 16 (none missed) for the usual rate. G3 passes, so the check runs hourly. As shipped, the warning can't fire until the 14 days before the latest week hold 200 or more new-prompt turns, so it needs two busy weeks of history before the latest week, and it wouldn't have fired during the August regression: replayed hour by hour from Aug 16, the 14 days before each week held 16–59 new-prompt turns until the daily check flagged the regression on Aug 22, and the open incident held it back after that. Over Sep 4–16 (549 new-prompt turns, 2 misses) the CUSUM raises no alarm at a usual rate of 0.2–1%.

- **Subagent models: no built-in agent keeps one model steadily enough.** Of 7 agent types other than general-purpose (4 of Claude Code's own: Plan, Explore, claude-code-guide and statusline-setup; plus 3 others), none had 5 or more days with 5+ responses and one model on 90% or more of them; the closest was Plan, with only 1 such day (100% on Opus 5), and Explore's busiest 2 days ran 56% on Sonnet 5. A caller can pick any subagent's model, so ccdrift only reports subagent models. G7 fails.
- **Early warning on tool-loop cache misses: passes on the main thread and in subagents.** A tool-loop turn (not opening with a prompt, not right after a compaction, within 5 minutes of the previous response of its transcript) misses when it reads less than half of what that response had cached: 10 of 10911 main-thread turns over 30 days and 104 of 48717 subagent turns over 26 days, from 2026-08-06 to 2026-09-16. A Bernoulli likelihood-ratio CUSUM against the miss rate of the 14 days before each week (at least 1,000 turns, held within 0.2% and half of p1) was tried with p1 of 1%, 2% and 5%, h from 2 to 8, and alarms counted only when their misses come from 1 or 2 sessions. False alarms were counted with the usual rate held at its 0.2% floor, the most sensitive rate the check runs at (outside Aug 16 – Sep 4 the tool-loop miss rates of these logs are below it), and planted 2% miss rates, seeded per start day, were caught against the measured usual rate. On the main thread (G8), p1 = 0.02 and h = 3 with 1 session raised no false alarm over the 10 days judged outside Aug 16 – Sep 4 and caught a planted 2% miss rate in a median of 87.5 turns (50 of 50 runs); one step lower, h = 2 raised 2 false alarms. In subagents (G9), p1 = 0.05 and h = 5 with 1 session raised no false alarm over the 9 days judged outside Aug 16 – Sep 4 and caught a planted 2% miss rate in a median of 148.5 turns (50 of 50 runs); one step lower, h = 4 raised 1 false alarm. Counting only alarms with misses from 2 sessions slowed the catch to a median of 536.5 turns at best on the main thread (45 of 50 runs) and 3959 turns at best in subagents (39 of 50 runs). No regression of tool-loop caching is known in these logs, so no alarm could be checked against a real one, and the days judged are few. G8 and G9 pass, so ccdrift warns about both.
- **Past incidents on the first run.** Before 0.5.0 a first check opened incidents only for flags that started within the last 14 days, so on these logs a first check on an empty state recorded nothing, although August held the caching regression. Replaying incident detection day by day over the history, as if the check had run each day, finds exactly that incident: flagged on the Aug 22 run from Aug 18 on 2.1.235 and 2.1.233 (~5.6M tokens re-cached by then) and back to normal on the Sep 7 run from Sep 4, ~16M tokens re-cached in all, the days the owner had recorded by hand, and nothing else. The replay of Aug 7 – Sep 17 takes under a second (3.6 s on the same judged turns repeated over 180 days), so the first check runs it on the history it reads.
- **A session start that changed only because the work moved (G12).** Until 0.8.0 ccdrift pooled every project's session starts, and the owner's logs produced one alert from that: "context ~130k -> ~54k from 2026-09-10". Nothing had changed. On 09-10 the work moved to two projects created that week, whose sessions start at ~46-54k, while the project that had been running held its level and started at ~128k on 09-16, six days after the "drop". Measuring each session against its own project's recent level instead (the median of that project's previous sessions, once it has at least 3), every session in the history sits between 0.92x and 1.30x, and the move between projects reads as nothing at all. The same measurement finds a change the pooled rule never saw: one project stepped from ~104k to ~128k on 2026-08-27 and stayed there (101-118k on 08-16..08-22, 126-136k from 08-27, still 128k on 09-16), its baseline ratios median 0.966 against the window's 1.227. Only that project had the 3 sessions each side of the step that a project needs before it can be compared with itself, so the alert says the project's own CLAUDE.md, MCP servers or skills explain it as readily as Claude Code does, rather than blaming the update. G12 replays the rule day by day: a history where the work simply moves to a smaller project holds no change where pooling finds one; every change reported on the real logs names a project whose own level moved; and a step planted across every project, halving each session from one day on, is caught on each of the last judgeable days, 4 of 4, skipping 2026-08-27, where the logs already report a change and a planted one could not be told apart from it. That plant exercises the pooled pass, which finds a machine-wide step on its own. The other half of the rule (the per-project pass, which finds a step in one project that the other projects' sessions dilute) is one these logs cannot test: a one-project plant only separates the two passes when it lands in a minority of the judged sessions, and the only folder here with enough sessions each side of a plantable day holds 19 of the 20 judged, so halving it halves the pooled set with it. The gate says so, "not measurable here" with those counts, and scores neither a catch nor a miss on it, the way it already reports a history with no project big enough to plant in. What pins the per-project pass instead is a balanced two-project history in `lab/test_context.py`, where halving one project moves no pooled median and the plant is caught 3 of 3, credited only on days the pooled pass is silent on. A machine with a second busy project would answer it on real logs. A step is only planted where the rule could see it: at least 3 judged sessions follow it in projects that were already being judged before it.
- **Failed requests and responses cut short: one day in six weeks stands out (G10, G11).** Over 2026-08-06 to 2026-09-17 (43 days, 31 of them with anything logged, all 31 active) the logs hold 9 failed requests that count (7 overloaded, 5 of them on 2026-09-03, and 2 cut off mid-stream), 4 more banners blaming the Mac for going to sleep, which `ccdrift report` counts but no rule alerts on, and 2 responses that stopped at the token limit, one on 09-15 and one on 09-16. Replaying both rules day by day, as the check would have run them each morning: with the settings 0.7.0 ships, requests failing (at least 5 in a day, at least twice the busiest of the judged days in the 14 before, at least 5 such days to compare with) alerts once, on 2026-09-03, within the budget of 1 alert per 30 days of history; responses cut short (at least 5 responses, at least 0.5% of the day's main-thread responses, 3 times the worst share of the judged days before, leaving out the days of the same run) never alerts. A burst was then planted on each of the last 5 days a rule could judge, one replay per planted day, each gate planting the shape its trouble takes: for G10 a single day carrying 10 failed requests, since an overload is a day (09-11, 09-14, 09-15, 09-16 and 09-17), and for G11 a three-day run with 1% of each day's responses stopping at the token limit, since a release that truncates responses keeps doing it until someone fixes it (runs from 09-09, 09-10, 09-11, 09-14 and 09-15, the last five judged days with room for a whole run). A plant counts as caught only when the planted replay alerts on a day of that plant which the unplanted history stayed quiet on (an alert the logs were going to raise anyway is no evidence), and for G11 any day of the run will do. Planting only on the last day of the logs, as the gate first did, measured how busy that day happened to be rather than the rule. Floor 5 / ratio 2 catches all 5 planted request bursts and G10 passes, while a ratio of 3 or more catches none, since 2026-09-03's 5 failures sit within 14 days of every planted day and a planted 10 doesn't treble them. Planting runs found a flaw in the cut-short rule itself: floor 5 / share 0.5% caught only 4 of the 5, missing the run from 2026-09-14, and the reason was that the run hid behind its own first day. That day holds 356 main-thread responses, so its 1% is 4 of them, one under the floor of 5, too few to report, while its 1.12% share became the worst day before the rest of the run, so 09-15's 6 of 579 (1.04%) and 09-16's 11 of 1084 (1.01%) would each have needed 3.37% to clear the ×3 comparison. A regression that began on a day too small for the floor was never reported at all, however long it lasted. The comparison now leaves out the unbroken run of days at or above the share that ends at the day being judged (the days of a regression are not the usual level, which is what `incidents.exclusions` already does for the cache metric), and a reported episode silences the days that carry its run on for as long as that episode is itself among the days judged, so one regression is one alert about every fortnight rather than one every few days: replayed day by day, a 20-day regression at 2.5% is reported twice, on its first day and 15 days later. With that, floor 5 / share 0.5% catches all 5 planted runs and G11 passes, and no real day of these logs alerts: the 2 responses cut short here are 1 a day, under every floor in the grid. Floor 3 catches all five runs too, at a share of 0.2% or 0.5%; floor 8, or a share of 1%, catches 2.

- **A cut-short run that deepens is reported again (G13).** `cut_short` now speaks a second time when a day stands CUT_RATIO (3) times above the share the covering episode last reported, whichever suppression (the 3-day spell or the run carrying on) would otherwise have held it, naming the level and day it escalated from as `worse_than`. G13 asks whether that holds on top of the flat-run guarantee G11 already covers: it plants a run of PLANT_RUN (3) days at an opening share, then PLANT_WORSE (3) more at 5 times it, and counts a plant as caught only when the planted replay alerts once on a day of the opening half and again on a day of the worsened half that the unplanted history stayed quiet on; it also plants the same run flat, at the opening share throughout, and requires that flat run to still alert exactly once, so a setting that simply speaks on every day of a run can't pass by claiming every escalation. The opening days plant at OPEN_SHARE (5%), not G11's smaller PLANTED_SHARE (1%): G13's premise is a run ccdrift already reported, deepening, and a plant that never clears CUT_FLOOR in the first place has no first alert to escalate from. Planting the opening days at 1% first, before settling on 5%, caught only 2 of the 5 plants: the other 3 opened on 2026-09-06, 09-07 and 09-08, quieter days of this history (342, 207 and 286 main-thread responses), where 1% rounds to 3, 2 and 3 truncated responses, short of the floor of 5, so the opening half was never reported and had nothing for the worsened half to escalate from, even though that worsened half, at 5 times the share, opened a new alert every time. That is a fact about the rule's reach on a small history, not a flaw in the escalation itself, and it is why G13 has to plant harder than G11: G11 only asks whether a small run is caught at all, G13 asks what ccdrift says about a run it has already caught. With OPEN_SHARE and WORSE_SHARE (25%, 5 times OPEN_SHARE) floor 5 / share 0.5% catches all 5 planted escalations and reports each flat run of the same length exactly once (`G13 floor=5 share=0.005 alerts=0 caught=5/5 flat-runs-said-once=5/5`), and every other setting in the grid does the same, including floor 8. What G13 can't show: these logs hold 2 responses cut short over the 43 days measured, one on 2026-09-15 and one on 2026-09-16, and the cut-short rule has never actually fired on them, so G13's evidence is about how the rule behaves on planted data, not about how it has behaved on this install's real traffic.

## Re-run on 2026-09-21

Every numbered gate above was re-run over the same logs carried forward to 2026-09-19, three days longer than the entries that record them. Seven kept their verdict on the setting ccdrift ships. Two did not, and neither turned out to be about the setting it appeared to indict.

- **Held, on the shipped settings.** G8 passes at p1 = 0.02, h = 3, 1 session and G9 at p1 = 0.05, h = 5, 1 session, both unchanged. G10 passes at floor 5 / ratio 2 with 1 alert over 45 days, on 2026-09-03 as before, and 5 of 5 planted bursts caught. G11 and G13 pass at floor 5 / share 0.005 with no alert over those 45 days, 5 of 5 planted runs caught, and every flat run still reported exactly once. G12 passes: 39 session starts across 7 projects, 26 of them judged against their own project, no alert on a move to a smaller project where pooling finds one, and 5 of 5 planted steps caught. Its one-project plant is still not measurable here, for the reason the G12 entry gives: the project a plant could land in holds 21 of the 26 judged sessions. G7 still fails, on more data than before: 8 agent types other than general-purpose, none with 5 or more active days and one model on 90% of its responses, while general-purpose itself ran 52,078 responses over 30 days at 62% on Sonnet 5.

- **G3 now passes at h = 5 rather than h = 4, on one day.** At the shipped h = 4 the CUSUM raises a single false alarm, and it is 2026-09-17: two new-prompt turns missed that day against a base rate of 0.43%, reading back 0.057 and 0.140 of what the previous response had cached. h = 4 still catches a planted 5% miss rate in a median of 35.5 turns (48 of 50 runs); h = 5 raises nothing and takes 45.0 turns (46 of 50). ccdrift keeps h = 4. Trading about ten turns of detection speed against one alarm on a day that genuinely missed twice is not a trade a single day in a 45-day corpus should decide, and recording the gap here means a second such day reads as a signal rather than a surprise. The same two turns are why 2026-09-17 scores z = -4.57 on the daily cache metric without flagging, and why the chart page's turn-by-turn probe now puts its first false-alarm-free threshold at h = 20: one day, three symptoms, not three findings.

- **G2 fails at a spread of 0.229, and the spread is three projects rather than a version.** The gate pools every project's session starts per version and asks that no version with 3 or more sessions vary by more than it did when the entry above was written. 2.1.278 broke that: 3 sessions, one in each of 3 different projects, all on 2026-09-21 while that day was still running, starting at 61.2k, 72.4k and 140.4k. That 2.3x range is the distance between projects, not Claude Code changing what a session starts with. 2.1.276's 0.106 is a real within-project spread, over 4 sessions in one project from 50.4k to 66.9k. What this failure measures is that G2 still asks the pooled question 0.8.0 stopped asking: ccdrift judges each session against its own project's recent level, G12 measures that rule and passes, and the pooled criterion survives here only as an entry older than the rule it describes. The shipped alert is left alone. The criterion was then fixed rather than left stale: the gate now takes the spread per version within one project, which is the level ccdrift judges a session at, and `version_table` keeps the pooled view for the reader alone. Re-run that way it reads 6 version-and-project groups with 3 or more sessions and a largest spread of 0.106, and it still fails, because `MAX_SPREAD` is 0.10. That 0.106 is a real one: 4 sessions of 2.1.276 in a single project, 50.4k to 66.9k. The bar was not moved to meet it. 0.10 predates the per-project grouping and was set against a pooled 0.057, so it is a round number carried over rather than a measurement of what the gate now reads, and what it should be is the open question this leaves. Against the shipped alert's own trigger, a 25% move with each session more than 12.5% off, a natural 0.106 has room under it; that is an argument, not a measurement, and it is not enough to move a cutoff on.
