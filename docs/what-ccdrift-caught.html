Claude Code session logs · Aug 6 – Sep 15, 2026

What ccdrift caught

ccdrift is a small experiment that reads Claude Code’s local session logs and looks for silent changes in service: the prompt cache missing more often, requests quietly routed to Haiku, or less thinking per response. Run against one developer’s logs, it surfaced a real caching regression and showed which of those changes a single person’s history can reveal.

A cache regression, day by day

Between Aug 16 and Sep 4, sessions in these logs ran Claude Code 2.1.233 through 2.1.258. In that stretch, turns that begin with a new prompt lost their conversation cache far more often than before or after. Each loss sent the whole conversation, 100k to 900k tokens, back as a fresh cache write, while only the system prompt and tool definitions were still read from cache.

How it was pinned down

  • New prompts, not pauses. Continuations after a tool call never missed, even after pauses of 5–60 minutes (0 of 89). New-prompt turns missed about as often after a short gap as a long one: 5.6% within five minutes and 7.3% after 5–60 minutes, Aug 21–31.
  • The break came at the start of the conversation. On a miss, the tokens still read from cache matched exactly what the session’s first request read: the system prompt and tool definitions.
  • Not an expired cache. After pauses of 5–60 minutes, 14 of the 15 misses on Aug 21–31 came right after a request that wrote a 1-hour cache entry, so the cache should still have been there.
  • The client version, not the date. On Aug 16–22, the only days when both kinds of version ran, affected versions missed 4.1% of new prompts (20 of 493) against 1.1% (1 of 93) for older ones. These counts predate the cleanup.
  • A matching public report. Issue #91707 describes the same turn-boundary misses, rising from 7.2% on 2.1.224 to 29.2% on 2.1.252, and measures a fix in 2.1.259. Issue #87966 shows the same cache read stuck at the system-prompt boundary.

Ruled out along the way

  • Claude Code choosing a 5-minute cache
  • Prompt size
  • Compaction
  • Model or speed switches
  • Interrupted or cut-off responses
  • Slash commands
  • A single project
  • Edits to memory or CLAUDE.md
  • Too many content blocks per prompt
  • The login-token refresh bug (probably)
  • Anthropic status incidents

The exact mechanism isn’t confirmed. Issue #91707 attributes it to hook context that Claude Code drops when it rebuilds the conversation for the next request, which changes an earlier message. These logs couldn’t confirm that: 34 of the 38 misses had no saved hook context before them, and transcripts store the conversation, not the request Claude Code sent.

What it cost

17.4Mextra tokens written to cache instead of read from it

38 new-prompt turns on the affected versions lost their conversation cache and wrote it again, beyond the roughly 700 tokens a normal turn writes. At Opus 5 API prices, a 1-hour cache write costs $10 per million tokens and a cache read $0.50, so the extra writes come to about $165. On a subscription, the same tokens count against usage limits instead of a bill.

What ccdrift can catch in these logs

To measure sensitivity, ccdrift plants an artificial drop in the logs and checks whether its detectors notice. The Aug 16 – Sep 4 incident is left out first. That leaves 12 clean days, with room to start the planted drop on Sep 9, 10 or 11: each start needs 7 days of baseline before it and 3 days after.

Turn by turn

These logs average about 2,000 responses a day, so 258 responses is about an eighth of a typical day. At h = 8 and above, every alarm on the recorded logs falls inside the incident, which is why its dates are passed to ccdrift with --incident. Below h = 8, no catch is credited: the unaltered logs raise an alarm of their own first.

Reasoning effort needs more than one person’s logs

Claude Code stores thinking as a signature rather than readable text, so ccdrift estimates thinking from signature length, which tracks the thinking tokens implied by logged output counts (r = 0.97). Over the 12 clean days, the daily share of output spent thinking moved between 0.33 and 0.67 as the work changed. A planted 70% cut in thinking tokens moves it less than that, so no size of drop was caught, on all turns or on the main thread alone. On synthetic logs with steadier traffic, the detector needs a drop of 40–70% (median 50%). Catching effort changes points to pooling data from many users.

Limits of this analysis

  • Some history is gone. Claude Code deletes transcripts after 30 days by default. During the analysis it removed part of Aug 15–16, which was enough to hide the incident from the detector’s first rule. Retention on this machine is now 365 days.
  • The flag rule changed after this incident. Counting 3 of any 4 days instead of 3 in a row catches it again, and the smallest drops caught in these logs stayed the same. On 5 synthetic 40-day logs it added no false flags on the cache ratio, effort or main-thread Haiku, but Haiku across all turns, which subagent bursts make noisy, was falsely flagged on 3 logs instead of 1.
  • One developer, one workload. Every number here describes these logs, not Claude Code users in general.
  • Twelve clean days. The detection results rest on three starting days.

How the numbers were made

Source
Claude Code transcripts in ~/.claude/projects, one row per API response, with the lines of each response merged and copies in other files dropped.
New-prompt turn
A main-thread response that follows a prompt the user typed, within an hour of the previous response, and not straight after a compaction.
Cache read ratio
Tokens read from cache divided by tokens read plus tokens written. Below 0.5 counts as a miss.
Daily detector
Each day’s mean compared with the previous 14 days, using their median and spread, with the spread floored at sampling noise. A metric is flagged once 3 of any 4 days in a row fall past the cutoff: −3.0 for the cache ratio, 3.5 for the others.
Planted drops
A drop of 5–70% starts on each chosen day and runs to the end of the logs. Only flags that the drop itself adds count as a catch.
